# 双人协作约定

参与者：`ZZZdragondYNGPHX`（仓库管理员）与 `MIYIZIII`（写权限）。
本仓库保留上游 Git 历史、许可证和贡献署名。`main` 是共同基准，任务按需认领。

## 一项任务的流程

1. 开工前沟通目标、涉及目录、接口依赖和已有任务的重叠情况。
2. 功能、重构及可能重叠的工作先建开发任务 Issue，指定一位主要负责人；小修复可直接开 PR。
3. 从最新 `main` 创建 `<类型>/<作者>/<任务简述>` 分支，一项任务对应一个短期分支。
4. 有重叠时先协商修改边界；公共接口可先单独合入，再分别实现依赖它的功能。
5. 开 PR，记录结果、范围和最小相关本地验证；未完成的工作用 Draft PR。
6. 合并前同步最新 `main`；作者处理冲突，并重新验证受影响的部分。
7. 核心改动经另一人批准，其余按允许自查的路径自行合并；统一 Squash merge。
8. 远端任务分支在合并后自动删除，作者清理本地分支。

分支例子：`feat/zzz/buffer-search`、`fix/miyi/candidate-position`。
简称 `zzz` 对应 `ZZZdragondYNGPHX`，`miyi` 对应 `MIYIZIII`。
提交与 PR 标题使用 `feat:`、`fix:`、`refactor:`、`docs:`、`test:` 或 `chore:`。

同步自己独占的任务分支可使用 rebase；若已推送，只对自己的分支使用
`git push --force-with-lease`。多人共用同一分支时先沟通，采用合并 `origin/main` 等不重写
他人历史的方式。`main` 禁止强推。

## 核心范围按影响判断

改动满足下列任意一项，即要求另一人审查：

| 影响 | 示例 |
| --- | --- |
| 输入与投递 | 按键、候选选择、会话、preedit、焦点、密码框、提交文本 |
| 用户数据与隐私 | 词库、笔记、配置迁移、凭据、发往外部服务的内容 |
| 跨模块依赖 | 公共接口、通信协议、共享状态、基础模型、依赖锁和生成器 |
| 安装与发布 | 安装、更新、卸载、打包、许可证和发布流程 |
| 协作规则 | 审查分类、分支规则、自动化工作流、编码代理指令 |

同一个 PR 涉及核心与普通改动时，整项 PR 按核心改动审查。
界面代码改变投递、保存或网络请求行为时同样属于核心。
AI 可辅助检查，但 GitHub 的批准由另一位有权限的人完成。

## 路径分类与新增模块

[CODEOWNERS](../.github/CODEOWNERS) 的默认规则要求两位协作者中的一位批准，PR 作者不能
批准自己的 PR。所有代码和未分类路径由此受到保护；后面的无 owner 规则列出允许自查的例外。

第一版允许自查：

- 普通 Markdown 文档；架构、协议、发布、协作及代理指令文档除外。
- `Logo` 下的 SVG/PNG 和 `.github/readme` 下的语言标签 SVG。
- `DesignSystem/src` 下直接存放的 CSS 样式文件。
- `.github/ISSUE_TEMPLATE` 下的表单与普通 PR 模板。

核心目录及治理文档在清单末尾重新指定 owner，优先于普通文档例外。
UI 源码、测试、脚本以及其他未分类文件默认互审；确认某个独立模块可自查后，
可以通过互审 PR 缩小它的审查范围。

新增模块首次接入必须互审：说明公共接口、数据流、持久化和安装影响，并在同一个 PR
中确定它的路径分类。需要自查时，添加明确的路径例外；核心文件或子目录随后重新指定 owner。
不要用整个 `src`、`platforms` 或所有测试目录作为自查例外。

GitHub 按路径判断，无法推断改动的业务含义。如果允许自查的文件开始承担核心行为或包含
执行代码，作者仍须申请另一人审查，并更新 CODEOWNERS。不确定的改动先互审。
协作约定、CODEOWNERS 和规则配置本身必须互审，不能在待合并 PR 中自行豁免其改动。

## main 的远端设置

规则配置保存在 [main.json](../.github/rulesets/main.json)，由管理员应用到 GitHub Rulesets：

- 所有修改通过 PR 合入 `main`，禁止删除和强推。
- 通用批准数为 0；修改有 owner 的文件时必须获得 Code Owner 批准。
- 不启用对所有 PR 的最新推送批准要求，保证普通改动可以自查合并。
- 推送新的可审查提交后，旧批准失效；合并前解决审查讨论。
- 只允许 Squash merge，并要求后续历史保持线性。
- 不配置常驻绕过者，不设置必需 CI 检查，不自动发布。

仓库合并设置只开启 Squash merge；默认提交标题取 PR 标题，正文取 PR 描述。
合并前检查最终提交中的实际人类及 AI `Co-authored-by`，不能只依赖分支提交里的署名。
开启合并后自动删除分支。

初始化协作规则的 PR 按仓库管理员已确认的方案合并，随后启用规则；之后的治理变更互审。
管理员修改 GitHub 设置时，同步更新本规则文件和协作约定，避免文档与远端漂移。

## 分支结束与清理

- 合并：GitHub 自动删除远端任务分支。
- 放弃或被替代：先检查是否有其他任务依赖该分支，保留所需提交，再关闭 PR 并删除远端分支。
- 本地：切换离开已完成的分支，删除本地任务分支，执行 `git fetch origin --prune`。
  Squash 后 Git 可能不认为原分支已合并；先核对代码已进入 `main`，再删除自己的该分支。
- worktree：确认没有未提交内容后移除自己的任务 worktree，再清理对应本地分支。

本地清理由各自执行，不自动删除另一人的本地分支。`main` 长期保留；以后需要旧版本维护
分支时，再通过互审 PR 补充规则。

## 验证

每阶段及任务完成时，只在本地执行最小相关验证。PR 记录命令、结果和仍未验证的内容。
文档或规则调整只检查相关文件；代码变更执行影响范围内的构建或测试。
合并前最后运行 `git diff --check`。远端配置仅只读核对，不触发 CI 或跨平台构建作为验证。
